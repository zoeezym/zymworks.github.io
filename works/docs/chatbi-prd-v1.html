一、产品概述

1.1 背景

  • 2025 年中国 BI 市场超 70% 产品已具备 AI 对话分析能力，但 2026 年调研显示 90% 已部署 ChatBI 的企业业务部门实际使用率不足 30%
  • 行业复盘结论高度一致：瓶颈不在模型能力（最先进模型 Text2SQL 准确率仅 64.5%），而在业务口径语义鸿沟与结果不可信、错误不可定位——"90% 准确率但无法定位错误的产品对企业是不可接受的"
  • 现有开源方案（DB-GPT、WrenAI 等）聚焦 SQL 生成准确率与平台能力，对"口径对齐"与"信任机制"两个落地瓶颈缺少产品化设计

1.2 产品定位

面向中文企业场景的对话式数据分析工作台：业务人员用中文问数，系统给出口径透明、可校验、可下钻的可信答案。

  • 引擎：基于开源 Text2SQL 框架 Vanna 2.0（MIT）二次开发
  • 两大产品主张：指标口径中心（解决口径对齐）+ 内嵌可信度层（解决结果信任）
  • 克制边界：MVP 不做写操作、全库任意查询、BI 建模

1.3 成功指标（可量化）

指标目标值说明
测试集通过率（北极星）≥ 85%50 问中文测试集，四级评估前两级（完全正确/正确但次优）计为通过
语义层消融提升≥ +20pt裸 schema 生成 vs 注入口径后生成，同测试集对比
口径歧义澄清覆盖率≥ 90%测试集内刻意埋设的口径陷阱题，触发澄清反问的比例
双通道交叉验证拦截 ≥ 2 类不一致第二模型独立重写 SQL 与主通道结果比对
SQL 生成 P95 时延< 5s含语义层检索注入
一键反馈闭环Top 问题 100% 进入修复队列标记 → 聚类 → 修复队列可视化

二、用户与场景

2.1 目标用户

用户特征核心诉求
业务运营/管理者（P0）不写 SQL，日常需要取数与经营分析中文问数即得答案，且能确认"这个数怎么算的"
数据分析支撑人员（P1）被 repeated 取数需求占用高频问题自助化，口径解释成本下降
质量负责人（P1）关注 AI 答案可靠性看到通过率、失败模式与修复进度

2.2 核心场景

  1. 经营复盘：业务负责人问"上个月华东区收入环比怎么样？"→ 系统澄清口径歧义 → 给出结论 + 图表 + 口径回显 → 下钻"哪个省份掉得最多"
  2. 日常取数：运营人员问高频问题 → 秒级可信答案，替代提数工单
  3. 质量巡检：质量负责人在可信度看板查看通过率、消融对比与反馈修复队列

三、功能需求（五模块 MVP）

优先级统一采用 MoSCoW。每个功能：描述（业务目标→技术手段→业务价值）+ 用户故事 + 验收标准（Given/When/Then）。

A. 数据源工作台

描述：为让业务数据安全接入对话分析（业务目标），提供 CSV/SQLite/MySQL 只读接入与表结构自动提取，执行前拦截 DML/DDL/高危语句（技术手段），使企业数据在零风险前提下进入问数链路（业务价值）。

  • A1 数据源接入（Must）
  • 用户故事：作为数据管理员，我希望接入 SQLite/MySQL/CSV 数据源并自动提取表结构，以便业务问答有数可查。
  • 验收标准：
  • Given 已准备电商示例库，When 管理员配置连接并点击"验证"，Then 状态显示"只读连接成功"并列出全部表
  • Given 连接串含写权限账号，When 保存数据源，Then 系统强制降级为只读会话并在界面提示
  • A2 只读护栏（Must）
  • Given 任意生成的 SQL，When 包含 INSERT/UPDATE/DELETE/DROP 等语句，Then 执行前拦截、不触达数据库，并向用户返回拦截原因
  • A3 内置示例数据集（Must）：电商经营库（订单/客户/商品/退款）+ 电信账单库（出账/话务/套餐），均为自建脱敏数据

B. 指标口径中心（语义层）——核心差异化

描述：为消除业务术语与数仓定义的语义鸿沟（业务目标），建立指标字典（口径/公式/时间口径/维度）、字段业务语义映射与同义词归一，并 RAG 注入生成链路（技术手段），使口径歧义类 Bad Case 显著收敛并通过消融数据验证（业务价值）。

  • B1 指标字典管理（Must）
  • 用户故事：作为业务管理员，我希望定义"实付收入=实付金额（不含退款）、按支付完成时间"这类口径，让 AI 的回答与业务定义一致。
  • 验收标准：
  • Given 指标字典为空，When 管理员新增指标并填写名称/口径说明/计算公式/时间口径，Then 指标进入字典并可被问答链路检索
  • Given 业务问题命中某指标，When 生成 SQL，Then 该指标口径随 RAG 一并注入且在答案中回显
  • B2 字段语义映射（Must）：物理字段 → 业务术语（amt_pay → "实付金额，不含退款"），表结构导入后可批量补注
  • B3 同义词与问句归一（Should）："卖了多少/营收/GMV"统一映射到标准指标
  • B4 口径覆盖率统计（Should）：已映射口径的表字段占比，识别语义层缺口
  • B5 消融对比（Must）
  • Given 50 问中文测试集，When 分别以"裸 schema"与"注入口径"两种模式运行，Then 看板展示两组通过率及差值

C. 对话式分析

描述：让业务人员用中文完成取数与多轮分析（业务目标），提供多轮澄清、SQL 生成与中文口径回显、图表呈现、下钻追问与执行失败自修复（技术手段），实现"会说话的查询器"到"可信分析助手"的跃迁（业务价值）。

  • C1 多轮澄清（Must）
  • Given 问题存在口径歧义（如"收入"含税与否、"上个月"自然月/账期），When 系统无法从口径字典唯一确定，Then 以选项形式主动反问，而非硬猜生成
  • Given 用户选择口径，When 重新生成，Then 答案按所选口径计算并回显
  • C2 答案卡片（Must）：结论先行 + 口径回显行 + 数据表格 + 图表（柱/线/占比）+ 可展开 SQL
  • C3 下钻追问（Must）：对"哪个省份/品类降幅最大"类追问保持会话上下文，生成对比视图
  • C4 SQL 中文回显（Must）：答案注明采用的口径定义（指标、范围、时间口径），可一键展开原始 SQL
  • C5 SQL 执行自修复（Should）：执行失败时定位原因（字段/语法/权限）并自动修正重试一次

D. 可信度层（内嵌评测）——第二差异化

描述：为解决"结果不可信、错误不可定位"的落地瓶颈（业务目标），内嵌四级答案评估、双通道交叉验证、执行透明与用户反馈闭环（技术手段），把黑盒答案变成可审计、可持续修复的可信答案（业务价值）。

  • D1 双通道交叉验证（Must）
  • Given 关键问答，When 主通道生成 SQL 后，Then 第二模型独立重写 SQL 并执行比对；结果不一致时答案降级为"建议人工核对"并展示差异点
  • D2 四级答案评估（Must）：完全正确 / 正确但次优 / 部分正确（范围或口径偏差）/ 错误；仅前两级计入通过率，评估结果在答案卡片展示
  • D3 执行透明（Must）：行数、耗时、命中的口径定义数、检索的 SQL 样例数随答案可展开查看
  • D4 用户反馈闭环（Must）
  • Given 任一答案，When 用户点击"有问题"，Then 进入后台按问题聚类并展示 Top 修复队列（状态：待修复/修复中/已修复）
  • D5 可信度看板（Must）：通过率、消融对比、失败模式分布（多表 join 语义漂移/时间边界/口径混合等）、修复队列进度

E. 分析报告

  • E1 会话转报告（Should）：将会话沉淀为分析报告（结论 + 图表 + 口径附注 + 建议），支持导出 Markdown/HTML
  • E2 口径附注（Should）：报告自动附带所引用的口径定义，保证结论可追溯

四、非功能需求

类别要求
安全全链路只读；SQL 执行前白名单校验；数据不出本机（可接本地 Ollama）
性能SQL 生成 P95 < 5s；工作台首屏 < 2s
部署Docker 一键部署；README 明示"基于 Vanna 2.0（MIT）二次开发"并附架构图
兼容Chrome/Edge 现代浏览器
合规引擎遵循 MIT；示例数据自建脱敏，不使用任何公司数据与代码

五、交互与界面

  • 高保真原型见 衡数ChatBI-原型.html（本地双击可运行，零外部依赖）
  • 五个一级视图：对话分析（默认）、指标口径中心、数据源工作台、可信度看板、分析报告
  • 对话分析采用"中央对话流 + 右侧口径面板"双栏结构：答案在左，本轮使用的口径与执行透明在右，强化"口径透明"的产品主张

六、数据需求

  1. 指标字典 schema：指标ID、名称、口径说明、计算公式、时间口径、维度、过滤规则、同义词组、状态（草稿/待评审/已验证）
  2. 50 问中文测试集：含刻意埋设的口径陷阱题（含税/不含税、自然月/账期、去重口径、同名异义字段），每题含预期 SQL 与预期答案
  3. 失败样本库：问题、生成 SQL、评估等级、失败模式分类标签
