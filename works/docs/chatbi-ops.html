1. 数据安全的四道防线

ChatBI 的风险点很集中：它能用自然语言访问全库数据，任何一层漏了，业务用户就能绕过原有报表系统的权限。

防线位置拦什么失效后果
第一道：数据源接入连接层只允许只读账号；表白名单外不可查全库裸奔
第二道：SQL 生成语法解析写操作、系统表、大表全扫数据被改或库被打挂
第三道：执行注入执行层租户过滤、行级权限、列级掩码越权看数
第四道：结果输出渲染层SQL 原文、原始行数、敏感字段信息泄露

四道防线必须独立生效。不能指望"模型不会生成危险 SQL"这一件事。

2. 数据源接入安全

2.1 接入要求

项要求校验方式
账号权限必须只读账号；保存时检测账号是否有 INSERT/UPDATE/DELETE 权限连接测试时执行 SHOW GRANTS（MySQL）或等价查询
绑定地址账号限定来源 IP 为 ChatBI 服务出口 IP连接失败即提示"IP 未在白名单"
表白名单每个数据源维护可查表清单，默认空，需管理员逐表勾选生成 SQL 后提取表名比对清单
敏感表标记含个人信息的表需标记级别，标记后自动套用列掩码配置时强制选择级别
凭据存储加密存储（KMS 或独立密钥），界面只显示"已配置"，不回显明文代码审计
凭据轮换每 90 天提醒；过期前 7 天告警定时任务
连通性断连自动重试 3 次，仍失败则数据源置为"不可用"，相关问句直接提示健康检查

2.2 只读护栏实现

不能只靠关键词黑名单。要求三层：

  1. 语句类型白名单：解析后只允许 SELECT。含 WITH 的也允许，但最终语句必须是 SELECT。
  2. 危险关键字黑名单：INSERT / UPDATE / DELETE / DROP / TRUNCATE / ALTER / CREATE / GRANT / LOAD_FILE / INTO OUTFILE / SLEEP / BENCHMARK 出现即拦。
  3. 执行层兜底：数据库账号本身无写权限。即使前两层被绕过，也写不进去。

第 3 层是最可靠的，前两层是为了给出清晰的失败提示。

2.3 大表保护

规则默认行为
无 WHERE 的聚合查询允许，但估算扫描量超阈值拒绝
无时间条件的明细查询拒绝提示"请补充时间范围"
扫描行数估算超上限拒绝提示缩小范围
笛卡尔积风险（join 无关联条件）拒绝提示补充关联条件

3. 输出层约束清单

#约束拦截位置违规时的表现
1业务用户看不到原始 SQL渲染层按权限判断按钮变灰，提示需要分析权限
2结论文案中的数字必须存在于结果集渲染层比对降级为纯数据展示 + 告警
3不使用无阈值程度词文本检测替换为带百分比的中性表述
4不做因果判断文本检测（"因为""导致""由于"）改为"同时观察到"
5敏感字段掩码结果集后处理手机号 138••••8321
6返回行数上限执行层 LIMIT截断 + 提示
7导出加水印导出服务水印含工号与时间
8未发布指标的口径不得引用检索层过滤只检索"已发布"状态
9结果不得跨租户执行层强制 tenant 过滤查询返回空 + 告警

第 2 条值得单独说：模型生成结论时容易把 1.28 万写成 128 万，或者把"环比下降"写成"环比上升"。渲染层比对数字能拦住大部分这类问题，这是成本最低的幻觉拦截手段。

级别定义字段示例展示规则导出

5. 审计日志

5.1 记录内容

事件字段
问数用户、租户、问句原文、命中指标、生成 SQL、执行耗时、返回行数、终端 IP、时间
权限拒绝用户、请求的数据域、拒绝原因
行级注入用户、注入字段、注入值、原 SQL、最终 SQL
配置变更操作人、对象、变更前后值、时间、复核人
凭据操作操作人、数据源、动作（新增/轮换/删除）、时间（不记明文）
导出用户、导出范围、行数、水印编号
权限变更操作人、被变更用户、角色前后值
语义层发布 / 回滚操作人、版本号、变更指标清单

5.2 约束

  • 日志独立存储，业务库删除不影响日志。
  • 日志不可修改，只能追加。
  • 查询日志本身也是审计事件。
  • 审计员角色只读，不能删除。
  • 支持按用户、按数据域、按时间段、按是否命中敏感字段四个维度筛选。

6. 发布流程

6.1 变更类型与管控

变更风险管控
提示词调整中必须跑全量评估集，通过率不得低于上一版 2pt 以上
语义层新增指标低走评审，发布后观察 3 天澄清触发率
语义层修改公式高必须提供影响分析 + 影子比对，灰度发布
模型版本升级中全量评估集 + 20 条真实会话回放，双跑一周
数据源新增中表白名单逐表确认，敏感表标记级别
权限规则变更高双人复核，变更后 24 小时内抽检 20 条会话
前端版本低常规灰度

6.2 语义层变更的影子比对

公式变更不能直接生效。流程：

  1. 新版本以 shadow 状态上线，不对外服务。
  2. 采集近 7 天真实问句（脱敏），用新旧两版分别计算，记录差异。
  3. 差异幅度超预期（如收入类指标偏差 > 2%）则暂停，人工核对差异原因。
  4. 确认无问题后切换为 active，旧版保留 30 天可回滚。

这条流程的价值：口径改了没人知道，业务拿两套数字对不上，是这类产品最致命的事故。

6.3 灰度与回滚

层级手段生效时间影响范围
提示词灰度按用户 hash 分桶 10% / 50% / 100%即时命中分桶的用户
语义层灰度按租户或按用户组即时指定范围
模型灰度按租户切模型5 分钟指定租户
功能开关单功能开关（如双通道验证、澄清机制）即时全局或单租户
版本回滚语义层一键切回上一版即时全局

回滚触发条件：通过率环比降 ≥ 5pt、单租户错误率 > 5%、出现数据错误客诉 ≥ 2 起。

8. SLA

级别定义响应恢复补偿
P0全租户不可用或数据错误外泄10 分钟2 小时按合同
P1主要功能不可用（问数不可用、SQL 全部执行失败）30 分钟4 小时按合同
P2部分功能异常（某数据源不可用、看板数据延迟）2 小时1 工作日—
P3体验问题（文案、样式、非核心交互）1 工作日按版本—

可用性目标：SaaS 99.5%，私有化 99.9%（按合同）。统计口径为月度，不含计划内维护窗口（需提前 3 天通知）。
