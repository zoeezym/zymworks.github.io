1. 这批作品在证明什么

原型证明"我能设计界面与流程"，Skill 包证明"我能把业务规则写成机器可执行的东西"。这两件事的能力要求完全不同：前者要有产品直觉，后者要能把模糊的业务语言拆成判定条件、边界、失败分支。

三个 Skill 共用一套方法，这套方法才是作品集里真正可复用的资产。

2. 通用方法：两层技能结构

2.1 结构

SKILL.md                    入口。写清什么时候用、怎么判、输出什么、什么情况不该用
references/                 领域知识。规则表、表结构说明、场景库、话术
scripts/                    可执行逻辑。判定引擎、CLI、自测

references 与 scripts 的分工是关键：规则写进 md 会被人改错，写进 py 会被业务看不懂。实际做法是——规则表的权威版本放在 references 里给人看，脚本读同一份结构化数据做判定。这样业务能审规则，研发能跑逻辑，两边不会漂移。

2.2 两层路由

层职责形态例子
L1 路由判断这是哪一类业务，走哪个分支意图识别 + 关键要素检查"这个合同要不要评审"→ 判定为审批类，进入契约受理
L2 规则在分支内按条件给出结论决策表 / 决策树"折扣 35%，客户非危险等级"→ 档位 B，需地市审批

做成两层的原因：单层规则表会膨胀到几百条无法维护；分两层后，L1 只有 5–8 个分支，每个分支内的 L2 规则表 20–40 条，各自可独立迭代。

2.3 每个包必须回答的五个问题

  1. 什么输入是合格的（必填要素清单）
  2. 缺要素怎么办（追问，还是拒绝）
  3. 判定结果有几种（含"无法判定"这一种）
  4. 每条规则出自哪里（可追溯）
  5. 怎么证明它是对的（selftest 覆盖哪些用例）

第 3 点是多数人漏掉的：判定系统必须有"无法判定"这个输出，否则遇到边界情况只能瞎猜。

3. 案例一：AI 审批（多业务子场景路由）

目录：AI审批skill（多业务子场景路由）/

包：contract-intake-router.zip（13 文件）、approval-review-advisor.zip（15 文件） 图：审批业务流程脉络图.html（36 KB）

3.1 业务问题

一个合同进来，要不要走审批、走到哪一级、需要哪些材料，原来靠老员工经验。新人判断错会导致两种后果：该审的没审（合规风险），不该审的审了（流程成本）。三个场景的判断逻辑还互相交叉，同一个合同可能同时触发折扣审批和危险等级审批，走严还是走宽没有统一标准。

3.2 做了什么

组件内容完成度
L1 路由按合同要素判定属于 S1 专线折扣 / S2 客户危险等级 / S3 楼宇物业套餐已实现
S1 规则折扣档位判定、档位 C 的效益评估分支、折扣基线查找、折扣矩阵已实现
S2 规则危险/非危险分岔、审批层级编码、开闭区间严格定义已实现
S3 规则从严到宽顺序匹配、四档链路、严格度单调关系、档位覆盖盲区已实现
跨场景取严链路、审批严重度标尺已实现（标尺为推演规则）
引擎approval_engine.py 27 KB，两包共用已实现
CLIreview_cli.py、intake_cli.py已实现
自测selftest.py 11 KB / 7 KB已实现
演示数据demo_handoffs.json 26 KB、demo_contracts.json 8 KB已实现

3.3 设计上值得讲的三点

  1. 区间开闭必须写死。 "折扣 30%–40%"到底含不含 40%，直接决定审批层级。文档里对每个区间标注了开闭，代码里用半开区间统一实现，避免"看起来一样实际差一档"。
  2. 覆盖盲区必须兜底。 S3 的四档无法穷尽所有情况，存在落在档位之间的合同。设计上给了一个兜底分支（走最严或转人工），规则表不追求覆盖所有可能。
  3. 跨场景取严。 一个合同同时命中两个场景时，取审批层级更高的一方，并把另一方的原因也带上，避免审批人只看到一半信息。

3.4 已知问题

问题影响处理
两个包共用 approval_engine.py，各存一份改一处忘另一处会不一致待合并为单包 + 一个共用依赖目录
references 内文件名在 Linux/Mac 解压后乱码（GBK 编码打包）跨平台不可用重新用 UTF-8 打包
审批严重度标尺是推演规则，未与业务制度逐条核对对外讲述时可能被质疑讲述时明确说明是设计推演

4. 案例二：智能比数

目录：智能比数skill/ 包：data-table.zip（6 文件） 图：黔南智能比数助手-对话页面原型.html（57 KB）

4.1 业务问题

业务人员每周要拿两份表格做比对：哪几行新增、哪几行消失、同一条记录的字段变了什么。用 Excel 手工做，几万行要几小时，还容易看错列。更麻烦的是每次比对的规则不一样——有时按订单号，有时按"手机号+日期"，有时要模糊匹配。

4.2 做了什么

组件内容
主脚本data_merge_compare.py 66 KB，处理合并、比对、字段差异、汇总统计
工具桥接_tool_bridge.py 19 KB，与运行时做参数与文件交互
操作说明references/operations.md 17 KB，写清每种比对模式的参数与输出格式
入口SKILL.md 12 KB，含何时用、参数怎么填、常见错误
前端对话式比对界面原型，支持多轮修改比对条件

4.3 设计上值得讲的两点

  1. 比对键必须由用户明确指定。 不能让脚本猜哪列是主键。猜错会导致全表都算差异，比不做更糟。所以 SKILL.md 里把"确认比对键"列为必填步骤，缺则追问。
  2. 输出拆成三块，不能混在一起。 新增集、消失集、变更集分开输出，变更集里再列字段级差异。混在一起的结果没人看得下去。

4.4 已知问题

问题影响处理
zip 内含 __pycache__ 与 .pyc仓库脏、跨 Python 版本可能报错打包前清理
与 ChatBI 项目的定位有重叠（都是对话式数据处理）面试讲述时容易混讲清区别：ChatBI 是"问数"，比数是"两份表的差异"，一个面向查询一个面向核对
无 selftest改动后无法快速验证补 10 条样例与期望输出的比对脚本

5. 案例三：网络域投诉工单诊断

目录：网络域投诉工单处理skill/ 包：sd-workorder-diagnosis.zip（5 文件，全 references，无 scripts） 图：工单看不见诊断决策树.html 笔记：看不见工单，场景分析以及日常处理方法.md

5.1 业务问题

一线报"看不见工单"，原因可能有 7 类：报文解析异常、工单被别人领走、卡在营服外勘、派单工号已离职、待班长派单、装维操作不规范、受理缺关键参数。每类的排查路径和处置动作都不同，新人只能问老员工。

5.2 做了什么

组件内容完成度
SKILL.md入口、判定顺序、输出现场处置建议已实现
场景库scenarios.md 6.7 KB，7 类场景已实现
表结构说明database_tables.md 10.9 KB，涉及的库表与关键字段已实现
案例库demo_cases.md 10.5 KB已实现
模拟数据mock_data.md 29 KB已实现
决策树独立 SVG，从"看不见工单"到 7 类场景的判定路径已实现
可执行脚本无未实现

5.3 这个包的核心价值

它是四个包里业务纵深最深的一个。7 类场景来自真实运维里反复出现的问题，其中"工单被别人领走"这类问题，表面是系统问题，实际是组织协作问题——处置动作是查出领单工号并告知，而不是改数据。

这类知识的产品化难点在于：它是判断经验，写不成严格的判定规则。 决策树是合适的载体，规则引擎在这里不合适，因为分支之间没有严格的互斥条件，更多是"先查什么、看到什么再查什么"的顺序判断。

5.4 已知问题

问题影响处理
只有 references 没有 scripts，不能真正执行更像知识库而非工具补一个查询辅助脚本（输入工单号 → 输出该查哪些表）
原始笔记含内部库名 lnrmdb_shandong、表名公开仓库的信息边界问题已在本仓库保留原笔记，但不应在对外材料中引用具体库名
决策树是 SVG 片段，不是完整 HTML双击打开显示异常补 <html><body> 外壳
mock_data.md 未说明与真实表结构的对应关系学习者不知道哪些字段是真的补一节字段映射说明

6. 四个包的横向对比

维度AI 审批智能比数工单诊断
业务纵深中（制度型）低（通用能力）高（经验型）
规则确定性高（可写成决策表）低（依赖用户指定）低（依赖顺序判断）
工程完成度高（引擎 + CLI + selftest）中（脚本强，无自测）低（纯知识）
可复用性中（绑定审批场景）高（任何表格比对都用）低（绑定特定系统表结构）
面试讲述价值高（能讲规则设计）中（能讲数据能力）高（能讲业务理解）

7. 面试怎么讲这批作品

7.1 90 秒版

我做了三个业务场景的 Skill 包，分别是合同审批路由、表格比对、网络工单诊断。它们共用一套方法：SKILL.md 做入口，references 放业务规则，scripts 做判定。 最关键的设计是两层路由。第一层判断这是哪类业务，第二层在分支内按条件给结论。这样规则表不会膨胀到无法维护，每个分支可以独立迭代。 审批那个包工程完成度最高，有判定引擎和自测。工单诊断那个包业务纵深最深，7 类场景都是真实运维里反复出现的，但它的判断是经验型的，用决策树比用规则引擎合适。 这批东西证明的是我能把模糊的业务语言拆成判定条件、边界和失败分支，并且知道什么场景该用规则、什么场景该用检索。

7.2 高频追问与落点

追问应答要点落点
为什么分两层单层规则表会到几百条无法维护；分层后 L1 只有 5–8 个分支§2.2
遇到规则覆盖不到的情况怎么办必须有"无法判定"这个输出，走兜底或转人工；盲目兜底比报错更危险§2.3、§3.3
怎么保证规则没写错selftest 覆盖边界用例，尤其是区间的开闭§3.2
知识型场景为什么不用规则引擎分支之间没有严格互斥条件，是顺序判断，决策树更合适§5.3
这几个包能直接上线吗审批包能跑但缺线上评估；比数包能用但缺自测；工单包是知识库不能执行§3.4、§4.4、§5.4
你觉得哪个做得最不好工单包。它只有知识没有执行，用起来还是靠人查§5.4

7.3 不要说的话

  • 不说"这套框架可以复用到任何业务"——不同业务确定性差异极大，这话一追问就崩。
  • 不说"准确率 95%"——没有评估就没有准确率。
  • 不把三个包说成三个项目——它是一个方法在三个场景的应用，说成一个方法更有说服力。
